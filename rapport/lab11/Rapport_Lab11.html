Résumé

Ce lab est le dernier bloc du projet SenEvent : il ne reste plus à ajouter de fonctionnalité, il faut mettre l'application web en ligne. Le client web existait depuis les labs précédents et fonctionnait en local, mais il n'avait jamais été construit pour la production ni déployé.

Le travail réalisé couvre six points :

  1. Build de production : réparer puis vérifier tsc -b && vite build en local.
  2. Projet Vercel : relier le dépôt GitHub au projet senevent-equipe-1, avec le bon Root Directory (apps/web) et les variables d'environnement Supabase.
  3. Réécriture SPA : faire en sorte qu'une route profonde comme /evenement/13 renvoie index.html au lieu d'une 404.
  4. Supabase Auth en production : Site URL, URL de redirection autorisées et confirmation d'email réactivée.
  5. Recette de production : dérouler les dix points du lab sur l'URL publique, en mobile émulé (390 × 844).
  6. Documentation et version : README racine avec la section « En ligne », déploiement continu et tag v1.0-web.

Le résultat est une application accessible publiquement, mise à jour automatiquement à chaque merge sur main, avec une prévisualisation par Pull Request.

1. Contexte et objectif

Le dépôt est un monorepo :

senevent/
  apps/
    web/          React + Vite + TypeScript  -> deploiement Vercel
    mobile/       Expo / React Native
  packages/
    shared/       types, client Supabase, fonctions metier
  supabase/
    migrations/   schema SQL et politiques RLS
    config.toml   configuration Auth
  .github/workflows/build-web.yml

Le client web et le client mobile partagent la même base Supabase et la même logique métier (@senevent/shared). Le Lab 11 ne modifie donc pas le comportement fonctionnel : il ajoute la chaîne de livraison et vérifie que tout tient debout en production.

Les contraintes du lab sont les suivantes :

  • un build reproductible (npm ci) à partir d'un seul package-lock.json ;
  • aucune variable secrète dans le dépôt ;
  • une URL publique stable ;
  • le rechargement direct d'une route profonde doit fonctionner ;
  • la confirmation d'email doit être active ;
  • une recette explicite, avec des preuves.

3. Étape 1 — Vérifier le build local

3.1 Le build de production

Le script de build du web enchaîne la compilation TypeScript et le bundler Vite :

cd apps/web
npm run build     # tsc -b && vite build

Le build produit dist/index.html et deux fichiers hachés (index-*.css, index-*.js). dist/ est ignoré par Git (apps/web/.gitignore), ce qui est le comportement attendu : le dossier est un artefact, pas du code source.

3.2 Prévisualiser le build

Avant de déployer, on sert le build local avec vite preview :

npm run preview
curl -sI http://localhost:4173/ | head -n 1
curl -sI http://localhost:4173/evenement/13 | head -n 1

Les deux routes répondent 200 en local. C'est le serveur de prévisualisation de Vite qui gère le repli SPA ; en production, ce rôle sera tenu par la réécriture Vercel.

3.3 Un seul package-lock.json

npm ci exige un lock unique et cohérent avec le package.json de la racine. Le contrôle révèle deux locks :

git ls-files | grep package-lock.json

# package-lock.json

Le lock de apps/web est supprimé, puis npm install régénère le lock racine. Le commit 900577f ne laisse qu'un seul lock pour tout le monorepo. C'est ce qui permet à Vercel et à la CI d'utiliser npm ci de façon reproductible.

3.4 Réparer le build avant de déployer

Le premier build de production échouait pour deux raisons cumulées :

  • des composants encore en .jsx alors que tsc -b attend des modules TypeScript ;
  • des imports de types non explicites, refusés par verbatimModuleSyntax.

La correction convertit EvenementCarte.jsx, SearchBar.jsx et Auth.jsx en .tsx, et ajoute les imports import type. Le commit 35174e0 rend le build vert.

Un second problème apparaît avec npm ci : apps/web demandait une version de React différente de celle du monorepo. La version est alignée sur 19.1.0, puis vérifiée :

Le correctif de build est mergé directement sur main (commit ef8df24) pour que la branche de production puisse construire l'application :

5. Étape 3 — Réécriture SPA et premier déploiement

5.1 Le problème des routes profondes

Une application React Router n'a qu'un seul fichier HTML. Quand l'utilisateur ouvre directement /evenement/13, le navigateur demande cette URL au serveur. Sans configuration, Vercel cherche un fichier evenement/13 qui n'existe pas et renvoie 404.

La solution est une réécriture : toute URL inconnue est servie par index.html, puis React Router affiche la bonne page.

{
  "rewrites": [
    { "source": "/(.*)", "destination": "/index.html" }
  ]
}

Le fichier est ajouté dans apps/web/, donc à la racine du projet Vercel (Root Directory). C'est un point important : placé à la racine du monorepo, il serait ignoré.

5.2 Le premier déploiement, volontairement incomplet

7. Étape 5 — Supabase Auth en production

7.1 Pourquoi configurer les URL

Après une confirmation d'email ou une réinitialisation de mot de passe, Supabase redirige l'utilisateur vers une adresse autorisée. Par défaut, cette adresse est http://localhost:3000. En production, il faut déclarer l'adresse Vercel et les adresses de développement locales.

Cette liste est une protection : Supabase refuse de rediriger vers une adresse inconnue, ce qui empêche un attaquant de détourner un lien d'authentification.

7.2 Configuration versionnée

La configuration est décrite dans supabase/config.toml :

[auth]
site_url = "https://senevent-equipe-1.vercel.app"
additional_redirect_urls = [
  "https://senevent-equipe-1.vercel.app/**",
  "http://localhost:5173/**",
  "http://127.0.0.1:5173/**",
]

[auth.email]
enable_confirmations = true

La capture montre les valeurs locales (site_url, additional_redirect_urls, enable_confirmations = true) puis supabase config push --yes. Le projet distant est synchronisé ("auth": "up_to_date"). La seconde occurrence de enable_confirmations à false concerne le bloc [auth.sms], désactivé : elle ne remet pas en cause la confirmation d'email.

7.3 Confirmation d'email

Avec enable_confirmations = true, un compte créé depuis l'interface n'obtient pas de session immédiate : l'utilisateur doit cliquer sur le lien reçu par email. C'est le comportement attendu en production, et c'est aussi ce qui a révélé un bug corrigé plus loin (section 10.1).

10. Bugs trouvés pendant la recette et corrigés

La recette n'a pas servi qu'à cocher des cases : elle a révélé deux vrais défauts de production. Les deux ont été corrigés par Pull Request, avec prévisualisation et merge.

10.1 Inscription avec confirmation d'email active

Symptôme. Avec enable_confirmations = true, signUp ne renvoie pas de session. Le code d'inscription tentait alors d'insérer le profil immédiatement :

const data = await sInscrire(email, motDePasse);
if (data.user) {
  await getSupabase().from("profiles").insert({ id: data.user.id, nom });
}

Sans session, la requête est anonyme et la politique RLS profiles_insert_self (with check (id = auth.uid())) la refuse. Le compte était créé, mais sans ligne profiles ; la clé étrangère evenements.organisateur_id empêchait ensuite de créer un événement.

Correctif. Le nom est passé dans les métadonnées du compte (options.data.nom), et le profil est créé à la première session, dans App.tsx :

useEffect(() => {
  if (!session?.user) return;
  const nom =
    session.user.user_metadata?.nom ||
    session.user.email?.split("@")[0] ||
    "Utilisateur";
  creerProfil(session.user.id, nom).catch(() => {
    // Profil deja present : rien a faire.
  });
}, [session]);

Auth.tsx affiche un message explicite (« Compte créé. Vérifiez votre email pour confirmer, puis connectez-vous. ») au lieu de naviguer vers l'accueil sans session.

La vérification en production confirme : après confirmation, le profil « Awa Recette » existe et l'événement peut être créé.

10.2 Navbar inutilisable en mobile

Symptôme. En 390 px de large, la barre de navigation débordait horizontalement et le bouton « Se déconnecter » n'était plus cliquable. La recette du point 9 ne pouvait pas continuer.

Correctif. Une media query sous 640 px fait passer la barre sur deux lignes et autorise le retour à la ligne des liens :

@media (max-width: 640px) {
  .nav {
    flex-direction: column;
    align-items: flex-start;
    gap: 0.6rem;
    padding: 0.8rem 1rem;
  }
  .liens {
    flex-wrap: wrap;
    gap: 0.6rem 1rem;
    width: 100%;
  }
  .email {
    width: 100%;
    overflow-wrap: anywhere;
    font-size: 0.82rem;
  }
}

Après merge et redéploiement automatique, la recette complète repasse : le bouton de déconnexion est accessible et le point 9 peut être vérifié.

12. Bilan et limites

12.1 Ce qui est livré

  • Une application web publique : https://senevent-equipe-1.vercel.app.
  • Un déploiement continu : merge sur main → production ; Pull Request → prévisualisation.
  • Une réécriture SPA qui rend les URL profondes partageables et rechargeables.
  • Une authentification Supabase configurée pour la production, confirmation d'email active.
  • Un README qui documente l'URL, la structure et les réglages.
  • Un tag v1.0-web sur la version testée.

12.2 Limites assumées

Limite Explication
Envoi d'email 429 Le service d'email intégré Supabase limite fortement les envois. La confirmation a été vérifiée avec un lien generateLink, équivalent du lien envoyé.
Point 8 non testé Pas de téléphone ni d'Expo Go dans l'environnement. Le mobile n'a pas été modifié par ce lab.
Recette en mobile émulé 390 × 844 dans Chrome, pas un vrai téléphone en 4G. Le rendu et les parcours sont vérifiés, pas la performance réseau.
Dépendances npm audit signale des vulnérabilités dans l'arbre de développement ; elles ne concernent pas le code applicatif livré.

12.3 Ce que la recette a apporté

La recette n'était pas une formalité : elle a mis au jour deux défauts qu'aucun test local n'aurait révélés dans ces conditions.

  1. Un défaut de logique d'authentification : l'inscription supposait une session immédiate, hypothèse fausse dès que la confirmation d'email est active — c'est-à-dire en production.
  2. Un défaut de rendu mobile : la navbar n'avait jamais été testée à 390 px.

Les deux ont été corrigés par PR, prévisualisés, mergés, puis revérifiés en production. C'est exactement le cycle que le lab cherche à installer : construire, déployer, observer, corriger, redéployer.
